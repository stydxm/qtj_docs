# 网络访问

现在我们已经能解释局域网内部的通信：

```text
本机 IP → 同网段目标
本机 IP → 默认网关 → 其他网络
```

但打开一个网站时还有两个问题：

1. 电脑通常使用 `192.168.x.x` 这类私有地址，互联网怎样把数据送回来？
2. 我们输入的是域名，不是 IP，计算机怎样找到对应地址？

::: tip
NAT、DNS 和 ISP 知识点。
:::

## 私有地址与公网地址

常见的私有地址范围：

```text
10.0.0.0    - 10.255.255.255
172.16.0.0  - 172.31.255.255
192.168.0.0 - 192.168.255.255
```

私有地址主要在一个组织、家庭或实验室网络内部使用。互联网不会直接为每一个 `192.168.x.x` 规划一条可以从任意地点访问的路由。

而公网地址是在更大互联网中可以被路由到的地址。

一台设备通常只知道自己的私有地址：

```text
我的电脑：192.168.1.20
```

如果把这种地址直接发送到互联网，远端服务器通常不知道怎样把回复送回来。

这时就需要 NAT。

## NAT : 网络地址转换

NAT（Network Address Translation，网络地址转换）常见于家用路由器和网络边界设备。

它大致完成下面的过程：

```text
内网设备发出数据
  → NAT 把源地址改写为公网地址
  → 同时记录这次连接对应哪个内网设备
  → 公网服务器把回复发到公网地址
  → NAT 根据记录改回内网地址
  → 数据交还给原来的内网设备
```

可以用一张简化表理解：

| 方向 | 地址变化 |
|:-|:-|
| 内网发往公网 | `192.168.1.20` → 公网地址 + 临时标识 |
| 公网返回 | 公网地址 + 临时标识 → `192.168.1.20` |

实际 NAT 不只看 IP，还会通过端口等信息区分多台设备。这一章不展开端口转换细节，只需要理解它是“改写地址并记住对应关系”。

### NAT 带来的两个结论

第一，内网设备主动访问互联网通常比较方便。

```text
内网电脑 → 路由器/NAT → 公网服务器
```

第二，互联网上的设备想主动连接内网设备，通常没有直接入口。

```text
公网陌生人 → ??? → 内网电脑
```

如果确实需要从公网主动连接内网设备，通常要做端口映射、内网穿透或借助中继服务。这些内容涉及安全和网络配置，这一章不展开。
> 我相信玩《我的世界》的同学们都主动(被迫)学习了这部分内容...

## DNS : 域名系统

DNS（Domain Name System，域名系统）负责把域名转换成 IP 地址。

例如：

```text
www.ros.org 常见网络地址
    ↓ DNS 查询
某个 IP 地址
```

人类更容易记住名字，计算机最终仍需要地址来发送数据。DNS 就是两者之间的翻译表。

需要区分两件事：

```text
DNS 解析成功：知道目标对应哪个 IP
网络访问成功：确实能够与那个 IP 和具体服务通信
```

所以“域名能解析”不代表网页一定打开，“网页打不开”也不一定是 DNS 坏了。

## ISP 和光猫

家庭网络访问互联网时，通常还要经过：

```text
内网设备
  → 家用路由器
  → 光猫
  → ISP
  → Internet
```

ISP 负责提供互联网接入，并把流量继续转发到更大的网络中。
::: tip
常见 ISP 服务商 : 中国电信 ，中国移动， 中国联通
:::
光猫通常负责光纤线路与以太网之间的转换；有些光猫还集成路由和拨号功能。实验室里可能不直接看到光猫，也可能通过校园网或专线接入，具体结构会不同。

## 一次网页访问的完整过程

把前面的内容串起来，假设我们打开 `https://www.ros.org`。

电脑首先通过 DHCP 获取 IP 地址、子网前缀、默认网关和 DNS 服务器等网络配置。当用户访问 www.ros.org 时，系统通过 DNS 将域名解析为目标 IP，并根据路由表判断目标是否位于本地局域网。若目标位于公网，数据包通常会发送至默认网关，由家用路由器进行 NAT 地址转换，将内网源地址映射为公网地址并记录转换关系。随后数据经光猫、ISP 网络到达目标服务器。服务器返回响应后，数据经过 ISP 回到 NAT 设备，路由器根据转换记录将其转发给对应的内网电脑，最终由浏览器接收。

### 完整链路

```text
浏览器
  → DNS 查询域名
  → 本机路由表选择网关
  → 默认网关
  → NAT 改写源地址
  → 光猫
  → ISP
  → 目标服务器
  → 原路返回 NAT
  → 内网电脑
```

## IP 和 TCP 的分工

这一章的主题是 IP，但看到网页访问时通常会同时听到 TCP。

可以用一句话区分：

> IP 主要负责寻址和转发，TCP 位于它之上，负责为很多应用提供可靠、有序的数据传输。

TCP 怎样建立连接、重传、控制拥塞，不属于这一章的内容。只需要知道，IP 找到目标不等于应用已经可靠地完成了一次数据交换。

## 动手看看 ：分层检查一次公网访问

下面每一步只多排除一个问题。

### 第一步：确认去公网的路线

```bash
ip route get 1.1.1.1 # 显然不是内网的ip
```

确认系统选择了哪个出口接口，以及是否经过默认网关。

### 第二步：测试公网 IP

```bash
ping -c 4 1.1.1.1
```
> 是由知名网络安全与内容分发公司 Cloudflare 与亚太互联网络信息中心（APNIC）共同运营的一个公共 DNS（域名解析）服务器地址。
如果这个地址可以访问，但任意域名都打不开，问题更可能在 DNS，而不是完全没有网络通路。

某些校园网、公司网络或防火墙会禁用 ICMP，所以 `ping` 失败不必然代表公网完全不可用。

### 第三步：查看 DNS 配置

Ubuntu 常用 `systemd-resolved` 管理 DNS。执行：

```bash
resolvectl status
```

找到当前使用的网络接口，观察它的 DNS 服务器。

不同版本和网络管理方式的输出会有所不同，只需要找与当前接口对应的 DNS 配置。

### 第四步：验证域名解析

```bash
getent hosts www.ros.org
```

如果成功，通常会输出：

```text
IP 地址  www.ros.org
```

这一步只证明域名解析成功，不证明网页服务一定能连接。

### 第五步：检查 HTTPS 服务

```bash
curl -I https://www.ros.org
```

`curl -I` 只请求响应头，不下载完整网页。

成功时通常会看到类似：

```text
HTTP/2 200
```

不同网站可能返回 `301`、`302` 或 `403`，但只要能看到 HTTP 响应，就说明网络和 TLS 访问至少已经走到目标服务。

### 第六步：对比结果

| 现象 | 更可能出问题的位置 |
|:-|:-|
| IP 能 ping，域名不能解析 | DNS |
| 域名能解析，curl 连接失败 | 目标地址、端口、防火墙或代理 |
| 域名和网页都正常 | 基本公网访问正常 |
| `ip route get` 没有可用路线 | 本机接口、地址或默认网关 |
| 所有公网目标都不通 | 局域网出口、网关或上游网络 |

## 常见问题

### 为什么别人不能直接访问我电脑上的服务

常见原因是你的电脑位于 NAT 后面，没有独立的公网入口。

同一局域网内访问通常只需要：

```text
被访问设备 IP + 服务端口
```

跨公网访问则需要端口映射、内网穿透或中继服务，并且必须考虑安全风险。

### 能打开一个网页，是不是网络就完全正常

不一定。一个网页可能来自本地缓存、代理或不同网络路径。排查问题时最好同时检查：

```text
路由
DNS
IP 连通性
具体服务
```

### 为什么 `ping` 一个域名和 `ping` 一个 IP 结果不同

`ping 域名` 会先经过 DNS 解析，再向得到的 IP 发送 ICMP。`ping IP` 跳过了 DNS。

因此：

```text
ping IP 成功，ping 域名失败 → 优先检查 DNS
两者都失败 → 优先检查路由、网关或目标是否允许 ping
```

## 小结

这一页的关键关系是：

```text
NAT：让私有地址可以访问公网，并记录返回路径
DNS：把域名转换成 IP
ISP：提供接入互联网的链路
IP：负责寻址与转发
```

到这里，局域网、公网和域名之间的主线已经连通。最后再把同样的知识放回虚拟机桥接和 NoMachine 远程桌面这两个实际场景中。
